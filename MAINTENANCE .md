## 1. Паспортная часть и общие положения

### 1.1 Назначение документа

Регламент определяет состав, периодичность и порядок работ по поддержанию программы «Array Sum» и её данных в работоспособном состоянии, а также зоны ответственности участников. Цели регламента:

- свести к минимуму простои и риск потери входных данных (`input.txt`);
- обеспечить целостность и восстановимость данных (резервное копирование, проверка копий, тестовое восстановление);
- обеспечить сохранение работоспособности и качества ПО при обновлении окружения (автотесты, обновление Python и программы);
- обеспечить предсказуемые действия при сбоях (инцидентное ТО);
- обеспечить сохранность данных (вынос копий на внешний носитель, контроль состава каталога копий).

### 1.2 Область применения

| Объект ТО | Состав |
|---|---|
| Программное обеспечение | Программа «Array Sum» (`main.py`); интерпретатор Python 3.8+ |
| Данные | Входной файл `input.txt`; резервные копии в папке `backups/` (формат JSON с контрольной суммой SHA-256) |
| Репозиторий | Репозиторий GitHub `DenisSamofalov/MASIV` |
| Аппаратная часть | ПК с ОС Windows, Linux или macOS; диск с достаточным свободным местом; внешний носитель или облако для копий |

Регламент не распространяется на обслуживание операционной системы, сети и самого сервиса GitHub.

### 1.3 Роли участников

| Роль | Ответственное лицо | Обязанности |
|---|---|---|
| Пользователь / оператор | Назначается на время эксплуатации | Выполняет плановое ТО (раздел 2.1): создание и проверка резервных копий, ведение журнала обслуживания (раздел 4) |
| Администратор / разработчик | Назначается на время эксплуатации | Выполняет обновления программы, запуск тестов и аварийное восстановление (раздел 2.2); актуализирует документацию |

### 1.4 Виды технического обслуживания

| Вид | Описание | Раздел |
|---|---|---|
| Плановое (профилактическое) ТО, ППР | Календарные работы, предотвращающие сбои и потерю данных | 2.1 |
| Внеплановое (инцидентное) ТО | Аварийные работы при отказах, ошибках и повреждении данных | 2.2 |

### 1.5 Используемые документы

Тест-кейсы (`docs/TEST_CASES.md`), правила работы с репозиторием (`docs/GIT.md`).

### 1.6 Условия начала работ

Перед началом любых работ необходимо:

- проверить версию Python: `python --version` (нужен 3.8 или новее; на Linux/macOS — `python3`);
- убедиться, что `main.py`, `input.txt` и папка `backups/` находятся в одной папке проекта;
- проверить, что `input.txt` содержит только целые числа и что на диске есть место для копии.

### 2.2 Внеплановое (инцидентное) ТО

#### Классификация инцидентов

| Приоритет | Признак | Срок начала работ |
|---|---|---|
| Критический | Потерян или повреждён `input.txt` и нет пригодных копий | Немедленно |
| Высокий | Повреждена копия; восстановлена не та версия; программа не работает после обновления | В течение рабочего дня |

Общий порядок: зафиксировать признаки и время инцидента → выполнить действия карты → убедиться в восстановлении работоспособности → записать инцидент в журнал обслуживания (раздел 4).

## 3. Контроль качества и отчётность

### 3.1 Параметры контроля

| Параметр | Как измеряется | Целевое значение |
|---|---|---|
| Актуальность резервной копии | Дата последней копии по `python main.py backups` | Копия создана в последний день работы с данными |
| Целостность копий | `python main.py backups` | Все копии со статусом «OK» |
| Контрольный пример | ТК-03 | Сумма равна 36 |
| Результат тестового восстановления | ТК-06 | Восстановление без ошибок, расчёт выполняется |
| Результат автоматических тестов | ТК-07 | Все тесты пройдены |
| Количество копий | `python main.py backups` | Не более 10 |
| Копия на внешнем носителе | ТК-04 | Выполнена на текущей неделе |

### 3.2 Оценка состояния системы

| Состояние | Условия |
|---|---|
| Норма | Все параметры контроля в пределах целевых значений |
| Требует внимания | Нарушен один некритичный параметр (например, не выполнен вынос копий на внешний носитель) |
| Неисправность | Нет актуальной корректной копии; `input.txt` повреждён; тесты или контрольный пример не проходят |

### 3.3 Порядок контроля и отчётность

Оператор фиксирует все выполненные работы и инциденты в журнале обслуживания (раздел 4). Администратор периодически проверяет журнал и значения параметров контроля. Изменения регламента вносятся через репозиторий отдельным коммитом (`docs: ...`) с обновлением версии и даты документа.
